# P4 성능 측정

WI-4.004(변경 감지 전송)의 측정 결과와 결정이다. 원시 기록은 `p4-performance.log`(`scripts/measure-flush.sh`가 남김).

## 조건

- kext 0.0.41, 게스트 2560×1600 (HiDPI, UI 1280×800), 전송 주기 16 ms, 타일 64
- 호스트 1920×1200, QEMU 10.0.13 GTK 창 1280×800 (`-device virtio-vga`)
- 게스트 vCPU 4개. `kernel_task` CPU는 vCPU 한 개 기준 % (`top`, 2초 간격 평균)
- 호스트 QEMU CPU는 사용자가 호스트 `top`으로 본 값

## 정지 화면 (2회, 각 30초)

| 변경 감지 | 게스트 `kernel_task` | 호스트로 보낸 양 | 부분 / 건너뜀 | 비교 시간 | 호스트 QEMU CPU |
| --------- | -------------------- | ---------------- | ------------- | --------- | --------------- |
| 끔        | 6.1% / 6.2%          | 25,188 MiB (약 840 MiB/s) | — | — | 4.2~4.9% |
| 켬        | 24.9% / 25.0%        | 0 MiB            | 1 / 1,425     | 5.2 ms/주기 | 4.2~4.9% (차이 없음) |

## 결정

- 기본값은 **꺼짐** (`Info.plist VVDirtyFlush=0`).
- 근거: 변경 감지에 가장 유리한 정지 화면에서도 호스트 QEMU CPU가 줄지 않았고, 게스트는 vCPU 한 개의 약 19%를 더 쓴다. 비교는 주기마다 16 MiB 화면과 shadow를 읽는 메모리 대역 한계라 타일 크기로 크게 줄지 않는다.
- 타이핑·동영상 장면은 재지 않았다. 바뀌는 영역이 생기면 전송이 늘어 정지 화면보다 이득이 작아지므로 결정이 바뀌지 않는다.
- 기능은 남겨 둔다. 호스트가 느린 환경에서는 boot-arg `vvideo_dirty=1` 또는 `sudo scripts/vvctl.sh dirty 1`로 켤 수 있다.

## WI-4.005 virtqueue 선택 feature

| 항목 | 값 (평소 사용 30초) |
| ---- | ------------------- |
| controlq 명령 | 101.5건/s |
| cursorq 명령 | 0.7건/s |
| 인터럽트 | 102건/s |
| 시간 초과 | 0 |

결정: `INDIRECT_DESC`·`EVENT_IDX` 모두 끔(구현하지 않음). 명령을 하나씩 보내고 기다리는 구조라 두 기능이 줄일 것이 없다. 켬·끔 비교 측정은 하지 않았다(사용자 승인). 자세한 근거는 PHASE-PLAN-04 결정 기록.
